# 远程连接方案（Android 版）

> **目标**：把「本机后端」换成另一台设备上的 DSH —— 电脑、另一台手机，都行。
> 装成插件，服务端与客户端**同一个插件**，**两边都装才能连**。

---

## 一、先说三个必须拍板的取舍

### 取舍 1：传输层不自建打洞，内置局域网发现 + 接受任何可达地址

**你说「用 p2p」，但真正的互联网 P2P 打洞需要一个 rendezvous 服务器** ——
而对端要互相找到对方，就必须有个双方都能访问的固定点。

**这和你「不能跨境」的要求直接冲突**：
- 自建 rendezvous = 我们得跑服务器，而且必须是境内节点（我们做不到）
- 用现成的公共 STUN/信令 = **那些服务绝大多数在境外**，等于每次连接都先出境

**所以方案是**：

| 场景 | 怎么连 |
|---|---|
| **同一局域网** | ✅ **内置发现**（UDP 广播 + mDNS），零外部依赖、零出境可能 |
| **跨网络** | ✅ **接受任何可达地址** —— 你填 `IP:端口` 就行 |

「跨网络」这一格是关键：**你机器上已经跑着 EasyTier**（我早前在进程列表里看到
`easytier-core`）。EasyTier / Tailscale / WireGuard / ZeroTier 这些工具
**本身就是专业打洞器**，它们给你一个虚拟内网地址 —— 我们的插件在那个地址上直连即可。

> **这样分工是对的**：打洞是网络层的事，有专门工具做得比我们好；
> 我们做 **DSH 层的协议**（发现、互认、后端替换、跨境闸）。
> 而且**不引入任何我们自己的服务器**，跨境风险归零。

**如果你坚持要内置打洞**：需要你提供一个境内的 rendezvous 节点（有公网 IP 的机器），
我可以按那个前提实现 UDP 打洞 + 中继回退。**这个前提需要你明确**。

### 取舍 2：「跨境」怎么判定 —— 分两种，规则不同

「不能跨境」有两种含义，必须分开处理，否则会误杀：

| 含义 | 判定 | 动作 |
|---|---|---|
| **对端在境外** | 对端地址是公网 IP 且**不在中国 IP 段内** | ❌ 拒绝连接 |
| **流量出境**（比如你开了全局代理） | 连接期间本机公网出口**不在中国 IP 段内** | ❌ **断开**并说明原因 |

**关键细节：私有地址跳过检查。** `192.168.x.x` / `10.x.x.x` / `100.64.x.x`
（EasyTier/Tailscale 用的 CGNAT 段）**不可能跨境** —— 它们是虚拟内网地址。
如果对它们也查 IP 归属，会把正常的内网连接判成境外。

判定用**内置的中国 IP 段表**（APNIC 的 CN 分配，约 8000 条 CIDR）：
离线、零依赖、零延迟。**不用在线 API** —— 那本身就是一次出境查询。

### 取舍 3：「同时」模式用侧边栏，而不是分屏

你说「同时是在右侧边栏显示远程的 DSH」。这条路正好走得通 ——
官方客户端有个**侧边栏浏览器面板**，而我们上一轮已经把它接通了
（桌面宿主载体 + 原生 WebView 承载，带金丝雀）。

所以「同时」= 主界面看本地、侧边栏看远程。**两个 DSH 并排，各自的会话互不干扰。**

## 二、架构

```

│  Kotlin 壳                                                        │

│    │                    ├─ 本地模式 → 本机引擎端口                 │
│    │                    ├─ 远程模式 → 隧道端口                     │
│    │                    └─ 同时模式 → 本机引擎 + 侧边栏 → 隧道端口  │
│    │                                                              │
│    └─ 设置 → 通用 → 「DSH 后端：本地 / 远程 / 同时」               │
│                                                                   │
│  Node 插件 dsh-fusion-remote（**服务端与客户端同一个插件**）        │
│    ├─ 角色由配置决定：serve / connect / both                       │
│    ├─ 隧道：本地端口 ⇄ P2P 通道 ⇄ 对端 DSH 的 web 端口             │
│    ├─ 互认：Ed25519 双向挑战 + 配对码                              │
│    └─ 跨境闸：握手校验 + 运行期出口监测                             │
└───────────────────────────────────────────────────────────────────┘
                            │
              局域网发现 / 你填的 IP:端口
                            │
┌─ 对端（电脑 / 另一台手机）────────────────────────────────────────┐
│  同一个插件，角色 serve：把本机 127.0.0.1:<web端口> 暴露给已认证的对端 │
└───────────────────────────────────────────────────────────────────┘
```

### 为什么隧道放在插件里，而不是让壳直连

三个理由：

1. **两边都必须装插件才能连** —— 这条你明确要求了。协议在插件层，天然满足
2. **互认与跨境闸都在插件层** —— 壳只负责「把 WebView 指到哪个端口」
3. **「同时」模式零额外代码** —— 侧边栏只是同一个隧道端口的第二个消费者

## 三、双向认证（防恶意远程控制）

**威胁模型**：有人扫到你的端口，想直接接管你的 DSH（等于拿到你设备上的工具执行权）。

### 三层防护

**第一层 · 双方都有密钥对（Ed25519）**
首次启动生成，私钥留在设备上（`~/.dsh/fusion-remote/identity.key`，权限 600）。
每次连接做**双向挑战应答** —— 双方都证明持有私钥，**不是单向认证**。
（单向认证意味着服务端认了客户端，但客户端不知道对面是谁 —— 那可以被中间人冒充。）

**第二层 · 配对码**
首次配对时，两边各自显示一个 **6 位码**（由双方公钥派生），**必须一致**。
用户核对后各点「确认」→ 双方把对方公钥**固定（pin）**下来。
之后连接只认这个公钥；**公钥变了会拒绝并告警**（防中间人）。

> 这一步就是 SSH 的 `known_hosts` 思路：安全性来自**首次使用时的人工核对**，
> 而不是来自协议本身。协议只能保证「你在跟同一个对端说话」。

**第三层 · 服务端必须显式开启**
默认 **`role = off`**。服务端要用户手动打开，并且：
- 只接受**已 pin 的**对端公钥
- 每次新连接弹**原生通知**，用户可拒绝
- 会话有**空闲超时**与**最大时长**
- 随时可一键断开所有

### 不做的事（明确划界）

- ❌ **不做「无人值守的开放服务」** —— 服务端永远需要人开
- ❌ **不做端口扫描发现** —— 发现只走局域网广播，不扫公网段
- ❌ **不把密钥写进日志** —— 桥的日志会经过 `/console`，密钥材料一律不进

## 四、跨境闸的实现

```
握手时：
  peer_addr = 对端地址（从 TCP 连接取，不信对端自称）
  if is_private(peer_addr):        # 192.168/10/172.16/100.64/…
      跳过检查                    # 内网不可能跨境
  elif not in_china(peer_addr):
      拒绝 + 记日志 + 通知用户
  else:
      允许

连接期间（每 30 秒）：
  if peer 是公网地址:
      出口 = 查本机公网 IP          # 只在需要时查
      if not in_china(出口):
          断开 + 通知：「检测到网络出口在境外，已断开远程连接」
```

**两个刻意的设计**：

1. **不信对端自称的地址** —— 用 TCP 连接的实际来源地址。对端说自己在中国没有意义
2. **本机出口只在「对端是公网」时才查** —— 局域网内查出口没有意义，而且那次查询
   本身就可能是出境的（讽刺但不罕见）

## 五、设置页的开关

```
设置 → 通用
  ┌────────────────────────────────────────────┐
  │ DSH 后端                                    │
  │  ○ 本地   只用这台设备上的 DSH               │
  │  ○ 远程   用远端设备的 DSH（本机不跑引擎）    │
  │  ○ 同时   本机照常，右侧边栏看远端            │
  │                                             │
  │  远端设备:  [ 已配对：书房电脑 ]  [管理]      │
  │  连接状态:  ● 已连接（出口：中国 · 局域网）   │
  ├────────────────────────────────────────────┤
  │ 作为服务端（让别的设备连过来）                │
  │  [ ] 允许远程连接        默认关闭             │
  │  已配对设备: 2 台          [查看] [全部断开]   │
  └────────────────────────────────────────────┘
```

**默认全是关闭状态** —— 装上插件不会自动开放任何东西。

## 六、能验证到什么程度

| 层 | 能不能验证 |
|---|---|
| 认证协议（挑战应答、pin 校验、配对码派生） | ✅ **能** —— 纯逻辑，可在 Linux 上跑测试 |
| 跨境判定（私有地址跳过、CN 段匹配、出口监测） | ✅ **能** —— 内置 IP 段表 + 可测的判定函数 |
| 隧道转发（HTTP / SSE / WebSocket 透传） | ✅ **能** —— 本地起两个进程对打 |
| 局域网发现 | ⚠️ 部分 —— 可测协议，但广播行为要看真机 |
| 设置页三选一 + WebView 路由 | ⚠️ 编译通过，**行为要真机** |
| 侧边栏显示远端 | ⚠️ 编译通过，**显示效果要真机** |
| **两端真机互连** | ❌ **必须有第二台设备** |

**底线**：认证、跨境闸、隧道这三块是**纯逻辑**，我会写成可测的模块并在 Linux 上跑通。
真机互连必须你来。
